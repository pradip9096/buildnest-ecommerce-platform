# `{@link}` to a Lombok-Generated Method Fails the `javadoc` Goal, Invisible to `./mvnw test`

## What happened

While eliminating BuildNest's `Product.stockQuantity`/`Inventory` dual source of truth (#485), a
new derived getter's javadoc referenced its data source like this:

```java
/**
 * Derived from {@link Inventory#getQuantityInStock()} — ...
 */
public Integer getStockQuantity() {
    return inventory != null ? inventory.getQuantityInStock() : null;
}
```

`Inventory.getQuantityInStock()` is a real, working method at runtime — generated by Lombok's
`@Getter` from the `quantityInStock` field. `./mvnw test` and `./mvnw compile` both succeeded
locally with no warning. Only PR #541's CI **Build & Test** check failed, with:

```
[ERROR] .../Product.java:89: error: reference not found
[ERROR]      * Derived from {@link Inventory#getQuantityInStock()} — {@code Inventory}
```

Two other CI checks (**Quality Gates**, **Security Vulnerabilities**) failed in the same run —
confirmed via each job's own log (not assumed) to be the *same* Maven build failure cascading, not
independent findings: the CI pipeline attaches `javadoc:jar` to the `package` phase, and all three
jobs depend on that same build succeeding.

## Why this is non-obvious

The intuition "this method exists, I can see it work, so `{@link}` can find it" is wrong for one
specific reason: the `javadoc` tool operates on **source text**, with no Lombok annotation
processing step. It sees `Inventory.java`'s literal file contents — a field and a `@Getter`
annotation, never a method declaration — so `{@link Inventory#getQuantityInStock()}` has nothing
to resolve against, even though `javac` (which *does* run annotation processors) compiles and
tests it without any complaint. `./mvnw test` never exercises the `javadoc` goal at all, so this
class of error is invisible locally unless you specifically run `./mvnw javadoc:jar` — a step this
repo's Maven `verify`/`test` targets don't include, only its CI `package` phase does (via
`maven-javadoc-plugin`'s `attach-javadocs` execution).

## Rule

Never write `{@link SomeClass#someMethod()}` (or `{@linkplain}`) pointing at a method that only
exists via a Lombok annotation (`@Getter`/`@Setter`/`@Data`/etc.) on the target class — javadoc
cannot resolve it, and the failure only surfaces in whatever CI step actually runs the `javadoc`
goal, not in a normal local test/compile cycle. Reference the underlying field or describe the
behavior in plain text/`{@code}` instead:

```java
/** Derived from {@code Inventory.quantityInStock} — ... */
```

If you need to verify a javadoc-touching change won't break CI, run `./mvnw javadoc:jar` (or
`./mvnw package`, which attaches it) locally before pushing — not just `./mvnw test`.
