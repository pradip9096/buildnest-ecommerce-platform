# Amendment Log for `development-workflow.md`

This file holds `development-workflow.md`'s own change history and self-maintenance rules, split
out (2026-08-02, mirroring the identical split already done for `work-on-issue.md`) so it isn't
part of what's loaded as standing project context on every session. `development-workflow.md`
itself carries a one-line pointer here; nothing in its operative content (the Sequence table,
Severity table, CI-failure handling, etc.) was lost, only relocated.

**Lives here, not in `.claude/rules/`:** Claude Code auto-loads every `.md` file under
`.claude/rules/` recursively as standing project context, regardless of whether anything points
to it — so a first attempt at this split that placed the file inside `.claude/rules/common/`
(alongside `development-workflow.md` itself) achieved nothing; it kept auto-loading every session
just like the file it was split out of. This file lives in `docs/knowledge-base/project/` instead,
a directory that is never auto-loaded, genuinely realizing the split's purpose. See Amendment #97
below.

## Amending This File

This applies to the whole file, not just the severity table — a loophole, ambiguity, or missing
case can turn up in any section (a risk-modifier category that should exist but doesn't, a CI
failure mode not covered, branch hygiene that doesn't fit some real situation, etc.).

**When to amend:** the moment a lessons-learned pass (`~/.claude/rules/definition-of-done.md`
item 5) surfaces something this file should have said but didn't — don't wait for it to recur
first. A single sharp edge case (e.g. one that caused real confusion or a mistake) is enough to
amend immediately; a soft judgment-call mismatch is enough after it recurs (per "Revisiting This
Table" above).

**How to amend:**
1. Make the actual edit to the relevant section — don't just log the problem without fixing it.
2. Add one line to the Amendment Log below: `#` (the last row's number + 1), date, the
   issue/session that triggered it, and what changed. Keep it terse — this is a log, not a
   changelog essay. **Always append the new row at the very bottom of the table.** Before adding
   a row, check the last row's `#` — the new row's number must be exactly one higher; if it isn't,
   you're about to insert in the wrong position. This has already been violated twice by date
   alone (originally log rows 14-15, since collapsed into the "1-29" summary row per Log Hygiene
   below) — the `#` column exists specifically because a wrong date is easy to
   miss on a skim, but a skipped or repeated number is not. If the gap being fixed could plausibly
   recur, tag the Change cell with a `[defect-class: <slug>]` marker — see "Revisiting This
   Table"'s Recurrence Tracking subsection (in `development-workflow.md`) for the convention and
   the escalation rule that applies once the same slug reappears. **If the amendment involved a
   real rejected alternative** (not a plain factual correction or a bug fix with only one
   reasonable answer), the entry must also state what was rejected and the concrete condition that
   would flip the decision back to it — the same "reserve and revisit" discipline "Revisiting This
   Table" already applies to the severity table's own defaults, made explicit at write time
   instead of added ad hoc (see the `30-60` collapsed Amendment Log row for a worked example:
   tightening `task-list-plan`'s Notes cell was chosen over splitting it into a new step, with the
   reserved fallback stated as "task lists consistently omit the verification-tier statement
   despite the requirement").
3. If the amendment reverses or contradicts an earlier entry, say so in the new entry rather than
   silently overwriting the history of why the rule existed.
4. **If the amendment inserts a new step into the Sequence table**: give it a new, permanent kebab-case
   `ID` at creation time (never reuse or renumber an existing ID), insert its row at the correct
   position, and renumber the `#` column for display only. Never reference the new step by its
   display number in any cross-reference, in this file or elsewhere — always reference its `ID`.
   This is the entire point of the ID column (see "The Sequence" above): it lets `#` shift freely
   on insertion without ever requiring a hunt through the file for stale number references. Also
   grep the whole file for stray total-step-count mentions in free prose (e.g. "the full N-step
   ceremony" in "What NOT to do") — the ID system doesn't catch these since they aren't
   cross-references, only a literal count that drifts on every insertion.
5. **When a Notes cell grows a standalone multi-part definition, enumeration, or worked example**,
   extract it into its own KB article and shrink the cell to a short pointer. This is now a
   general, repo-wide rule, not specific to this table — see
   [Extracting Inline Content Out of Other Project Docs](README.md#extracting-inline-content-out-of-other-project-docs-rule-files-etc)
   in the KB README for the qualitative trigger, mechanics, and the periodic-re-check note (that
   general version was itself generalized from this item's original narrower wording — see
   originally Amendment Log entries 18-21, all four now folded into the "1-29" collapsed
   summary row per Log Hygiene below (theme 9 covers 18-19, theme 10 covers 20-21)). **Before
   writing the new article, search the KB's own Index for an existing article that already covers
   the same ground** (by keyword/topic, not just by filename) — a cell being extraction-worthy
   (large, standalone, contains a worked example) doesn't mean no prior article already exists for
   it. Confirmed near-miss on the `solution-options-adr` extraction (see the `30-60` collapsed
   Amendment Log row): a full draft duplicating the already-published "Recurrence Escalation for
   Process and Amendment Mechanisms"
   article was nearly committed before a manual check caught the overlap — the extraction trigger
   itself gave no signal that duplication was happening.
6. **Log hygiene**: once the Amendment Log passes roughly 20 entries, collapse entries older than
   the most recent 10 into a single "Earlier amendments" summary row per theme (one sentence each,
   not a list of every historical entry) — mirroring the identical rule already in
   `~/.claude/rules/definition-of-done.md`, reused here rather than invented separately. Give the
   collapsed row a range (e.g. `1-19`) instead of a single number so the next new entry's expected
   number stays checkable (one higher than the last *kept* row's number, ignoring the collapsed
   range). The point of the log is to explain *why* current wording exists, not to be a complete
   historical archive — git history already serves that purpose for anyone who needs full detail.
   **While collapsing, glance at the dates on the entries being folded** — if the last 20 entries
   span a shrinking number of days/issues compared to the 20 before them, that's a growth-rate
   signal worth naming to the user explicitly (not silently absorbing it into the collapse), since
   an accelerating Amendment Log is exactly the "process overhead now outpacing what it catches"
   risk `retro-issue.md`'s own proportional-depth scaling (its Amendment #3) was designed to guard
   against, just observed at the config-file level instead of the per-issue-audit level. This is
   not a new standing check run on every issue — it only fires at the collapse trigger that's
   already happening, so it costs nothing extra on the common path.
