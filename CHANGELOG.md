### Fixed
- The OWASP `Cache NVD database` step (`ci.yml`) keyed its cache on a `hashFiles('**/pom.xml')` hash — since the NVD CVE dataset is an external source unrelated to this project's own dependency versions, any `pom.xml` change (a routine version bump, a suppression-adjacent edit) invalidated the cache and forced a full multi-hour NVD re-sync from scratch instead of a fast incremental delta. Discovered when three separate PRs (#335, #337, #338) each independently hit ~1.5-2 hour full syncs during the #332 CVE remediation work. Rekeyed to a daily date-based key (`nvd-db-${{ runner.os }}-${{ date }}`) with an OS-scoped `restore-keys` prefix fallback, fully decoupled from `pom.xml` (#342)
- **master's `OWASP Dependency-Check` CI gate had been failing for at least 2 days** (`failBuildOnCVSS=7`, `pom.xml`) on genuine CVSS≥7.0 findings across ~20 dependencies, several at 9.0+ including one at 10.0 (`netty-transport`). Real fixes via version bumps: `spring-boot-starter-parent` 3.5.10→3.5.16, `spring-cloud-dependencies` 2024.0.2→2025.0.3 (the actual Boot-3.5-compatible release train — 2024.0.x targets Boot 3.4), `springdoc-openapi-starter-webmvc-ui` 2.0.4→2.8.17 (bundles a patched `swagger-ui`/DOMPurify), `elasticsearch-java`/`elasticsearch-rest-client` 8.18.8→8.19.18, `log4j2`/`tomcat`/`netty`/`micrometer` version-property overrides past what Boot 3.5.16 itself still pins. The `elasticsearch-java` bump introduced a new transitive dependency on Jackson **3.0.0** (`tools.jackson.core`, a brand-new major release with its own fresh CVEs) — overridden to 3.2.0. **5 confirmed false positives** documented in `owasp-suppressions.xml`, each independently verified against the actual NVD CVE detail page (not just CPE-pattern suspicion): `angus-activation` (the real CVE is in `org.eclipse.angus:smtp`, already fixed by this project's `jakarta.mail` 2.0.5), `kotlin-stdlib` (a Kotlin *build-cache/compiler* deserialization CVE — this project never runs Kotlin build tooling, only consumes the compiled stdlib jar at runtime), `micrometer-registry-prometheus` (the CVE is in the Prometheus *server's* `/api/v1/read` endpoint, not the client-side exposition library), `netty-transport`/`netty-transport-native-unix-common` (CVE only affects Netty 4.2.0–4.2.12, this project is on 4.1.136.Final), `httpcore`/`httpcore-nio` (CVE affects HttpComponents Core **5.x**, a different artifact lineage from the legacy 4.x branch this project uses, which has no HTTP/2 support at all). Along the way, fixed two pre-existing bugs of the fix's own making: the `owasp` Maven profile's `dependency-check-maven` instance (v10.0.4 — the one CI's `-Powasp` run actually invokes) had **no `<suppressionFiles>` wiring at all**, silently discarding every suppression; and the suppression XML itself violated the schema (`<until>` must be an attribute on `<suppress>`, not a child element), which silently voided every suppression until fixed (#332)
- `com.example.buildnest_ecommerce.model.entity` package sat at 63.28% instruction coverage, failing the `jacoco-check` gate, entirely because of `model.entity.CustomUserDetails`, an unused class with 0% coverage. The issue as filed (#323) asked for unit tests to close the gap; verification against the repo showed the class was a dead duplicate — `security.CustomUserDetails` (the one actually implementing `UserDetails`) is what `CustomUserDetailsService` and every controller test construct, and already has full test coverage. Removed the dead duplicate instead of testing unreachable code — the root-cause fix, not a workaround to hit a number (#323)
- **SEC-15**: access and refresh JWT tokens were stored in `localStorage`, readable by any XSS anywhere in the app for the full 30-day refresh-token lifetime — violated this project's own documented rule (`react/security.md`: "never store sessions in localStorage"). Tokens now travel as httpOnly, `Secure` (profile-conditional), `SameSite=Lax` cookies (`AuthCookieService`), set by `login`/`refresh` and cleared by `logout`; the JSON response body no longer carries raw tokens (`AuthUserResponse`, `userId`/`username` only). `JwtAuthenticationFilter` reads the cookie (falls back to the `Authorization` header for non-browser clients). CSRF protection re-enabled via `CookieCsrfTokenRepository` double-submit pattern (`SecurityConfig`/`TestSecurityConfig`) — only `/api/auth/login` and `/api/auth/register` are exempt, since every other endpoint is now a cookie-driven, state-changing action a forged cross-site request could abuse. New `GET /api/auth/csrf` bootstrap endpoint. Frontend: `client.ts` sends `credentials: 'include'` and attaches `X-XSRF-TOKEN` on mutating requests; `AuthContext` no longer touches `localStorage` or decodes JWTs client-side, rehydrating via a live profile call instead; the `token` parameter was mechanically removed from ~20 API functions and ~18 components (single TypeScript-enforced pass, not a compatibility shim) (#282)
- Enabling CSRF surfaced a confirmed Spring Security defect ([GH-12141](https://github.com/spring-projects/spring-security/issues/12141)): `CsrfAuthenticationStrategy` clears the `XSRF-TOKEN` cookie on every authentication event but fails to regenerate it within the same request/response cycle. Because `JwtAuthenticationFilter` re-authenticates on every single stateless request (no session), this fired on effectively every request and silently broke all mutating endpoints — invisible to sequential curl-based testing, only reproduced under the app's real concurrent request pattern in a browser. Fixed via `NonClearingCsrfTokenRepository`, a wrapper that ignores null-token (clear) saves; the CSRF token is refreshed only by the app's own `/api/auth/csrf` bootstrap and login/refresh responses. Documented in the class's own javadoc and in `spring-security.md` so a future refactor doesn't remove the wrapper without understanding why it exists (#282)
- `SecurityConfig` (the production security filter chain, including the SEC-14 CSP hardening from #237 that removed `unsafe-inline` from the main API chain) is `@Profile("!test")` and never loads during a test run — `TestSecurityConfig`, the hand-maintained test double used instead, had drifted: single filter chain with no Swagger isolation, and a CSP of just `"default-src 'self'"` missing `script-src`/`style-src`/`frame-ancestors`/`form-action` entirely, plus a missing `preload(true)` on HSTS. The #237 fix had zero regression coverage as a result. Extracted `SecurityHeaderPolicies` as the single source of truth for `MAIN_CSP`, `SWAGGER_CSP`, and `HSTS_MAX_AGE_SECONDS`, referenced by both `SecurityConfig` and `TestSecurityConfig` so the two configs can no longer drift apart without a compile error. New `SecurityHeadersTest` asserts the main-chain CSP has no `unsafe-inline` and matches the shared policy, plus frame-deny and HSTS (verified against a simulated-HTTPS request, since Spring Security only emits HSTS on requests it considers secure) (#312)
- The Admin Audit Log tab showed "An unexpected error occurred" / "0 entries" on almost every real-world visit despite real entries existing — `AuditLogService`'s `@Cacheable` methods (`getAllAuditLogs` and 4 sibling filter methods, all with the same defect) returned a raw Spring Data `Page<AuditLog>`, which serializes to Redis fine on a cache miss but cannot be deserialized back out on any subsequent cache hit (`PageImpl` has no default constructor or Jackson creator) — the first request to any given page "poisoned" that page's cache entry for the full 15-minute TTL. Introduced `AuditLogPageDTO`, a plain, Jackson-round-trippable class (`content`/`totalPages`/`totalElements`/`number`, matching the shape the frontend already reconstructs) and applied it to all 5 `@Cacheable` methods, not just the one endpoint currently wired to a controller. Deliberately non-generic rather than a generic `PageResult<T>` — a generic type has the same reified-type problem Jackson has with `PageImpl`, just one level down (a cached `List<T>` deserializes each element as a raw `LinkedHashMap` without explicit type info); a concrete `List<AuditLog>` field avoids that ambiguity entirely. New `AuditLogCacheSerializationServiceTest` reproduces the exact Redis serializer configuration from `CacheConfig` (no live Redis needed) and proves both the original bug (raw `PageImpl` throws on deserialize) and the fix (the DTO round-trips cleanly across two consecutive reads, matching the issue's exact reproduction steps) (#307)
- Admin Overview and Users tabs both failed with a generic error and no data — `!user.getIsDeleted()` auto-unboxed a `null` `Boolean` for at least one legacy user row, throwing an NPE that was caught by a bare `catch (Exception e)` with **no logging at all**, making the real failure invisible server-side. Fixed all 7 recurring call sites of this unguarded pattern (`AdminServiceImpl` ×3, `UserServiceImpl` ×2, `OrderServiceImpl` ×2) to `!Boolean.TRUE.equals(x.getIsDeleted())` — null-safe, and correctly treats a null flag as "not deleted" rather than throwing. Added `log.error(...)` to every previously-silent `catch (Exception e)` in `AdminReportController` (5 endpoints) and `AdminUserController` (4 endpoints), so a real failure is diagnosable going forward. Added Liquibase changeset `20260705-015-backfill-null-is-deleted-flags` to backfill existing `NULL` `is_deleted` rows on `users`/`orders` to `false` (guarded with `preConditions` — neither column is created by any Liquibase changeset in this repo, the same drift class as #305's `products`/`cart_items`; both only exist via Hibernate) (#306)
- `CartServiceImpl.addToCart` snapshotted `product.price` (full price) on every add-to-cart, never checking `product.discountPrice` — every discounted product on the storefront was silently overcharged relative to its advertised price, all the way through order confirmation (the same `price` snapshot flows into `OrderItem` at checkout). New cart items now snapshot `product.getDiscountPrice()` when set, falling back to `product.getPrice()` otherwise — matching the frontend's existing `discountPrice ?? price` display convention (`ProductCard.tsx`). Added Liquibase changeset `20260705-014-correct-cart-item-prices-for-discounted-products` to re-snapshot price on existing, not-yet-checked-out `cart_items` rows affected by the bug (guarded with `preConditions onFail="MARK_RAN"` on `products`/`cart_items` existing — neither table is created by any Liquibase changeset in this repo, the same drift class documented in #289's `20260704-012` changeset; both only exist via Hibernate). Already-placed, already-billed orders are deliberately **not** auto-corrected — `docs/reports/cart-price-correction-2026-07-05.md` gives a read-only audit query to identify potentially overcharged historical orders for manual finance/refund review, since retroactively rewriting a settled `order_items` price is a business decision, not a code fix (#305)
- `CartServiceImpl.getCartByUserId` and `WishlistServiceImpl.getWishlist`/`getWishlistProducts` threw a "not found" exception for a brand-new user who hasn't added anything yet — both Cart and Wishlist are lazily created on first *write* (`addToCart`/`addProduct`), but their read paths treated "no row yet" as an error rather than empty, surfacing a red error banner instead of the existing empty-state UI on `/cart` and the Wishlist account tab for the majority of first-session users. Both read paths now return an empty `CartResponseDTO` / empty `Wishlist` (`Set.of()` products) when no row exists yet, instead of throwing. Write-adjacent paths that act on an existing cart/wishlist (`clearCart`, `removeProduct`, `clearWishlist`) are unchanged — those legitimately have nothing to act on for a brand-new user (#303)
- `shipping_methods` had zero rows in a fresh environment (no seed data existed for this table), blocking every checkout at the shipping-options step — `ShippingServiceImpl.getShippingOptions` calls `findAllByIsActiveTrue()` with no fallback, so an empty table meant checkout could never complete on a fresh deploy or in a freshly-provisioned test/staging environment. Added Liquibase changeset `20260704-013-seed-default-shipping-method` inserting one active "Standard Delivery" flat-rate method. Verified the changeset applies correctly via a new standalone `ShippingMethodSeedMigrationTest` that runs Liquibase directly against a throwaway H2 connection (not `@SpringBootTest`) — the `test` profile's `ddl-auto=create-drop` runs Hibernate schema regeneration *after* Liquibase and drops/recreates every entity-mapped table including `shipping_methods`, discarding the seeded row before any `@SpringBootTest` body could observe it; production's `ddl-auto=validate` has no such conflict (#304)
- Added explicit `type="button"` to 31 non-submit `<button>` elements across 19 files that the new `react/button-has-type` lint rule flagged (re-enumerated fresh rather than trusting the audit's original count of 48 — the codebase had changed enough since the audit that the real count was different): `OrderDetailModal`, `OrdersTab` (account + admin), `WishlistTab`, `AuditLogTab`, `InventoryAdjustModal`, `InventoryTab`, `UsersTab`, `CartItemRow`, `ErrorMessage`, `Pagination`, `CategorySidebar`, `ImageGallery`, `QuantitySelector`, `ReviewsSection`, `AccountPage`, `AdminDashboardPage`, `CartPage`, `ProductDetailPage`. Every genuine submit button (login, register, checkout address step, address book save, security/password change, profile save) was left as `type="submit"` (#299)
- `PasswordResetController.changePassword`: **critical IDOR** — the endpoint accepted `userId` as a client-supplied `@RequestParam` with no check that it matched the authenticated caller. Any authenticated user could call `POST /api/password/change?userId=<victim>&oldPassword=<guess>&newPassword=<new>` and, given the victim's current password, take over their account. `userId` is now derived exclusively from `@AuthenticationPrincipal`, matching the pattern already used in `AddressController`. The issue as filed (#249) didn't mention this — it only flagged the credentials-in-URL problem below (#249)
- `PasswordResetController.changePassword`: credentials (`oldPassword`, `newPassword`) moved from URL query params to a JSON `@RequestBody` (new `ChangePasswordRequest`) — passwords no longer appear in server access logs, browser history, or `Referer` headers. **Correction to the issue as filed**: #249 stated the backend "expects a JSON body" and the existing query-param call would fail — that was incorrect. The endpoint used `@RequestParam` for all three fields and the existing frontend call worked exactly as the backend expected; switching only the frontend to send JSON without this backend change would have broken the endpoint (#249)
- `frontend/src/api/user.ts`: `changePassword` now sends `{ oldPassword, newPassword }` as a JSON body instead of URL query params, and no longer takes or sends `userId` at all (#249)
- `SecurityTab.tsx` / `AccountPage.tsx`: `SecurityTab` no longer takes a `userId` prop — nothing in the component needs it now that the backend derives the acting user from the auth token (#249)
- `SecurityTab.tsx`: password fields had no `id`/`htmlFor` association between `<label>` and `<input>` (same class of gap fixed elsewhere in #286) — added (#249)
